# Роли и журнал действий

Реализовано на первом этапе [roadmap](ROADMAP.md). REST-контракт — [OpenAPI](../api/openapi.yaml), миграция — `20261107200000_add_roles_and_audit.sql`.

## Полномочия

Участник всегда имеет базовую роль `user`. Дополнительные роли можно совмещать. Блокировка — отдельный статус аккаунта, а не роль.

| Возможность | user | moderator | support | admin |
| --- | --- | --- | --- | --- |
| Обычные действия участника | Да | Да | Да | Да |
| Модерация публичного контента (`content.moderate`) | Нет | Да | Нет | Да |
| Обработка обращений (`support.handle`) | Нет | Нет | Да | Да |
| Назначение ролей и блокировки (`users.manage`) | Нет | Нет | Нет | Да |
| Просмотр аудита (`audit.view`) | Нет | Нет | Нет | Да |
| Чтение обычных личных диалогов без участия | Нет | Нет | Нет | Нет |

Сами чат, очередь поддержки и инструменты модерации контента появятся на следующих этапах. Сейчас реализованы политика полномочий, управление аккаунтами и аудит. `auth.User.Can` — общая серверная проверка для HTTP и будущего WebSocket. Неизвестные полномочия запрещены.

`GET /api/v1/auth/me` возвращает публичные поля профиля, `roles` и `permissions`, с `Cache-Control: no-store`. Публичный `GET /users/{id}` не раскрывает роли, статус, email или служебные полномочия. После отзыва прав следующий HTTP-запрос уже проверяет новые значения из БД. UI перепроверяет сессию при её обновлении и после своих служебных изменений; мгновенное закрытие служебного экрана в других вкладках будет добавлено вместе с WebSocket. Сервер запрещает им операции сразу после отзыва прав.

## Первый администратор

Зарегистрировать обычный аккаунт, подтвердить email, затем на компьютере с конфигом и доступом к PostgreSQL из `services/api` выполнить:

```powershell
go run ./cmd/admin-bootstrap -c ./config.yaml -username ВАШ_ЛОГИН -reason "Первоначальная настройка администратора"
```

Вместо `-username` можно передать `-user-id UUID` из ответа `/api/v1/auth/me`. Эти параметры взаимоисключающие. На Windows для нужной версии Go используйте [инструкцию локальной разработки](LOCAL_DEVELOPMENT.md).

Команда применяет миграции и назначает администратора **только существующему активному аккаунту**, если активных администраторов ещё нет. Она не создаёт пользователя, не задаёт пароль и не отправляет письмо. После первого назначения повторный bootstrap отклоняется; дальнейшие назначения выполняются администратором. Причина и системный источник первого назначения сохраняются в аудите.

После обновления страницы профиля появится ссылка **«Управление сообществом»** (`/admin`). На ней можно искать участников по нику/имени, совмещать роли, блокировать/разблокировать аккаунты и читать журнал. Для поиска доступны и заблокированные участники. Сервер возвращает до 20 результатов при запросе из интерфейса; при большем количестве следует уточнить имя.

Обновление API требует перезапуска процесса: миграции выполняются при старте. Старый бинарник с запросами к `user_profiles.role` несовместим с новой схемой. Перед обновлением действующей базы нужно сделать резервную копию; процедура production-выпуска и отката остаётся инфраструктурным этапом roadmap.

## Административный API

Все маршруты требуют действующей сессии и серверной проверки полномочий, ответы не кэшируются:

- `GET /admin/users?q=...&limit=20` — поиск по нику/имени, включая заблокированные аккаунты; `q` от 2 до 200 символов.
- `GET /admin/users/{id}` — профиль, роли и статус для управления.
- `PUT /admin/users/{id}/roles` — полный набор `roles` и обязательная `reason` от 3 до 1000 символов после удаления пробелов по краям.
- `PUT /admin/users/{id}/status` — `status: active|blocked` и обязательная `reason`.
- `GET /admin/audit-events` — журнал с `cursor`, `limit`, `actor_id`, `target_id`, `action`, `from`, `until`. Начало периода включительно, конец исключительно, время RFC3339; фильтры сохраняются между страницами.

Базовый путь всех операций — `/api/v1`. Для браузерной записи Origin должен совпадать с Host; `Sec-Fetch-Site: cross-site` отклоняется. Vite proxy сохраняет исходный Host. JSON обязателен; запросы без Origin допустимы для локальных инструментов с действующей cookie.

Набор ролей всегда содержит `user`, не содержит повторов или неизвестных значений. Сервер нормализует порядок. Повтор уже установленного набора/статуса возвращает 204 и не добавляет событие.

Нельзя снять права или заблокировать последнего **активного** администратора: возвращается `409 LAST_ADMIN_REQUIRED`. Назначения, блокировки и bootstrap берут одну транзакционную блокировку, поэтому два одновременных запроса не могут лишить проект всех администраторов. Права исполнителя заново проверяются после получения блокировки, чтобы конкурентный отзыв роли не оставил устаревшие полномочия.

Блокировка атомарно отзывает все существующие сессии. Создание сессии берёт разделяемую блокировку строки активного аккаунта, а блокировка аккаунта сначала обновляет его статус, затем отзывает сессии. Незавершённый вход либо создаёт сессию до блокировки и попадает под отзыв, либо получает отказ. Разблокировка прежние сессии не восстанавливает — требуется новый вход. Уже начатые обычные HTTP-операции могут завершиться; управление аккаунтами повторно проверяет доступ внутри защищённой транзакции.

## Аудит и хранение

В `user_profiles.roles` хранится массив ролей с базовой `user` и ограничениями БД. Миграция переносит существующие `user/moderator/admin` без потери прав. `access_control_lock` содержит единственную строку для сериализации служебных изменений.

`audit_events` содержит UUID, время, тип и ID исполнителя, действие, тип и ID объекта, причину, request ID и разрешённые изменения `before/after`. Текущие действия:

- `admin.bootstrap` — первое назначение из локальной команды, `actor_type=bootstrap`, `actor_id=null`.
- `user.roles_changed` — изменение набора ролей.
- `user.status_changed` — блокировка/разблокировка.

Изменение состояния и успешный аудит сохраняются в **одной транзакции**. Если запись аудита не удалась, роли, статус и отзыв сессий откатываются. Неуспешные попытки не выдаются за совершённые изменения; технические ошибки идут в отдельный лог API.

Данные `changes` формирует сервис из разрешённых полей; исходное тело HTTP-запроса туда не копируется. Пароли, SMTP-реквизиты, коды, токены и содержимое переписки не записываются. Причина — свободный текст администратора, поэтому секреты в неё вводить нельзя.

У журнала нет API редактирования/удаления. Триггер БД дополнительно запрещает UPDATE, DELETE и TRUNCATE. Это не защита от владельца БД, который может изменить схему; отдельная политика хранения и архивирования должна предшествовать очистке. Откат миграции удаляет аудит и не сохраняет совмещённые роли/`support`; для действующей базы следует использовать исправляющую миграцию или проверенное восстановление резервной копии.

Redis и ClickHouse для этого этапа не нужны. Источник истины — PostgreSQL.

## Проверки

Добавлены проверки матрицы полномочий, регистрации без служебных ролей, сохранения старых ролей миграцией, отказа в повышении прав обычному участнику/сотруднику, отзыва прав с прежней сессией, одновременного bootstrap и снятия ролей, защиты последнего администратора, отзыва сессий, отката при сбое аудита, фильтров/страниц журнала и запрета изменения записей.

Frontend проверяет очистку служебного кэша при отзыве прав, сохранение полномочий при загрузке аватара, запрет служебных запросов обычному участнику, понятную ошибку последнего администратора, управление с клавиатуры и отсутствие горизонтального переполнения на 393 и 1440 px.

GitHub Actions (`.github/workflows/checks.yml`) запускает PostgreSQL-интеграцию с race detector, Go vet/build, проверку воспроизводимости sqlc, YAML/ссылок OpenAPI, frontend test/build и Playwright. Проверка OpenAPI здесь не заменяет полную проверку спецификации внешним валидатором.
