# Архитектура КлёвЛиги (согласуемый проект)

Текущая реализация: React/Vite в `apps/web` и Go/PostgreSQL API в `services/api` уже существуют. Ниже сохранены целевые решения архитектуры; фактические DTO, ограничения и временно недоступные операции описаны в [API_NOTES.md](API_NOTES.md). Frontend использует реальный `/api/v1`, а тесты подменяют HTTP-ответы.

Актуальные границы MVP и порядок реализации определены в [ROADMAP.md](ROADMAP.md). Совмещаемые роли, управление аккаунтами и аудит уже реализованы; личный чат, поддержка и WebSocket следуют следующими этапами. Детали доступа — в [ROLES_AND_AUDIT.md](ROLES_AND_AUDIT.md).

## 1. Состав MVP

- Публичная главная лента тем и отчётов, сортировки и поиск.
- Регистрация, вход и восстановление доступа, подтверждение email.
- Профили: ник, аватар, регион, описание, список публикаций.
- Форум: категории, темы, ответы, цитаты, редактирование своих материалов.
- Рыболовные отчёты: дата, водоём, текст, фото, виды рыбы, приватность места.
- Каталог водоёмов и страницы с привязанными отчётами/обсуждениями.
- Подписки на темы и водоёмы, мини-окно уведомлений с анимированным поплавком, REST-история и доставка событий через WebSocket.
- Личные текстовые диалоги и отдельный чат поддержки.
- Совмещаемые роли `user/moderator/support/admin`, модерация, жалобы, блокировки и транзакционный журнал действий в PostgreSQL.

После MVP: групповые беседы и вложения чата, бизнес-барахолка, AI-помощник, рейтинги и спортивные достижения, сложная карта глубин, платная подписка.

## 2. Система

```
                   ┌────────────────────────┐
                   │ React + Vite (браузер) │
                   │ TanStack Query + Router│
                   └────────────┬───────────┘
                                │ HTTPS JSON /api/v1
                   ┌────────────▼───────────┐
                   │ Go modular monolith    │
                   │ HTTP → middleware →     │
                   │ modules → repositories │
                   └──┬───────────┬─────────┘
                      │           │
            ┌─────────▼─┐    ┌────▼────────────┐
            │ PostgreSQL│    │ S3-compatible   │
            │ (+PostGIS) │    │ object storage  │
            └───────────┘    └─────────────────┘
```

Фронтенд и backend развиваются раздельно в одном репозитории. OpenAPI — общий контракт; текущий frontend подключён к Go-серверу через `/api/v1`.

## 3. Рекомендуемый backend-стек

- Go (актуальная стабильная версия), router `chi`, middleware логирования/восстановления panic/лимитов.
- PostgreSQL + `pgx`, `sqlc` для типобезопасных SQL-запросов или чётко документированный слой repositories; миграции `goose`.
- Валидация DTO на API-границе; доменные ошибки превращаются в устойчивые HTTP-коды.
- Авторизация: серверные сессии + HttpOnly Secure SameSite cookies (в случае разных доменов и OAuth настройки отдельно); CSRF-защита для write endpoints.
- Email: отдельный адаптер/провайдер; пароли хэшировать Argon2id.
- S3-compatible uploads: presigned PUT, подтверждение загрузки, серверная проверка MIME/размера, удаление GPS EXIF.
- Request ID, structured logs, health/readiness, OpenTelemetry по мере необходимости.
- Docker Compose для локального окружения, CI на lint/test/build/migrations/OpenAPI validation.

## 5. API-правила

- Базовый путь `/api/v1`.
- Ответы с пагинацией: `{items: [], next_cursor: string|null}`; курсор, не offset, для ленты.
- Идентификаторы UUID, время ISO 8601 UTC; публичные slug отдельно от ID.
- `GET` публичных материалов доступен без входа; запись требует пользователя.
- Единый формат ошибки `{error:{code,message,request_id,fields?}}`.
- File upload: `POST /media/uploads`, затем PUT в хранилище по выданному URL, затем `POST /media/uploads/{id}/complete`.
- Для повторяемых POST предусмотреть `Idempotency-Key` там, где возможны повторы/платежи (позже).
- Короткие перечни пользовательских опций можно вернуть отдельными справочными endpoints.

## 6. Масштабирование и события

Целевой MVP: один экземпляр Go API, PostgreSQL, REST и общий авторизованный WebSocket-канал для уведомлений, личных сообщений и поддержки. История хранится в БД; события отправляются после commit, пропущенное восстанавливается из истории. S3 добавляется для фотографий отчётов. Аудит служебных действий сохраняется в одной транзакции с изменениями; технические логи ведутся отдельно.

Redis добавляется при необходимости обмена событиями между несколькими экземплярами API или измеренной потребности во временных данных. ClickHouse рассматривается для аналитической копии большого потока событий. PostGIS, карты и AI-помощник следуют отдельными этапами после MVP. Детальные зависимости и критерии выпуска — в [ROADMAP.md](ROADMAP.md).

## 7. Безопасность и приватность

- GPS-координаты рыболовных точек **приватны по умолчанию**. Публичное местоположение отчёта — название водоёма, не точная геометка.
- Удалять GPS EXIF из загружаемых фото и не отдавать исходники, содержащие геометки.
- Rate limit логина, публикаций, комментариев; защита от бот-регистраций и спама.
- Серверная проверка прав на удаление/редактирование; audit log модерации.
- Для публичных страниц форума важен SEO: SPA удобна для разработки, но для продукционного продвижения тем и водоёмов следует заранее запланировать SSR или корректное серверное пререндеривание, sitemap, meta tags и canonical URL. Floot self-host export рендерит страницы в браузере.

## 8. Принципы фронтенда

- Не переписывать дизайн с нуля. Использовать экспортированные TSX + CSS Modules как визуальный эталон.
- React Router и TanStack Query; API-клиент генерировать из OpenAPI по согласованию команды.
- Минимум глобального состояния; фильтры страниц хранятся в URL, пользовательские сессии в auth provider.
- На стадии миграции mock-данные остаются, затем заменяются хуками query/mutation.
- 360/393/768/1280/1440 px — контрольные ширины; фокус, клавиатура, читабельные кликабельные зоны >=44px на мобильном.
