# Roadmap КлёвЛиги

Рабочий план по состоянию репозитория и обсуждениям на 7 ноября 2026 года. Этапы ниже описывают предстоящую разработку; наличие функции в плане не означает, что она уже реализована. Календарные сроки определяем после оценки отдельных задач.

## 1. Отправная точка

| Направление | Уже есть | Что предстоит |
| --- | --- | --- |
| Аккаунты | Код подтверждения email, создание сессии после подтверждения, вход/выход, ограничения auth-запросов | Подтверждённая доставка почты, восстановление пароля, удобная повторная отправка кода |
| Профиль | Обновлённая карточка с иллюстративным фоном, загрузка очищенного аватара в PostgreSQL | Редактирование данных и публичный профиль с публикациями |
| Форум | Категории, создание/просмотр тем, ответы, проверка родительского ответа, курсорные страницы | Цитирование в UI, редактирование своих материалов, управление темами и обработка жалоб |
| Социальные функции | Подписка/отписка в API, создание и чтение списка уведомлений | Список подписок, прочтение уведомлений, счётчик, мини-окно и доставка в реальном времени |
| Рыболовные отчёты | Создание, списки, связь с темой и водоёмом | Рабочая загрузка фотографий и проверка приватности во всех выдачах |
| Служебные роли | Совмещаемые `user/moderator/support/admin`, политика полномочий, bootstrap, управление аккаунтами, транзакционный аудит и экран администратора | Использование полномочий в будущих WebSocket, поддержке и модерации контента |
| Общение | Будущий сценарий согласован на уровне обсуждения | Личные диалоги, поддержка и WebSocket ещё не реализованы |
| Эксплуатация | Локальные инструменты, регрессионные проверки, Caddy-конфигурации, SMTP TLS и диагностика DNS | Воспроизводимое развёртывание на VPS, автозапуск, резервное копирование и проверка восстановления |

Регрессии изоляции личного кэша, скрытия удалённых материалов и пагинации сохраняем при всех дальнейших изменениях. Статус реального домена и доставки email проверяется отдельно от готовности кода.

## 2. Целевые решения для MVP

- React/Vite, Go API, PostgreSQL и Caddy. Первый релиз рассчитан на один экземпляр API.
- Один авторизованный WebSocket-канал для событий чата, поддержки и уведомлений. История и состояние прочтения сохраняются в PostgreSQL; REST остаётся для загрузки истории и восстановления после разрыва соединения.
- Четыре роли: `user`, `moderator`, `support`, `admin`. Служебные роли можно совмещать; базовые пользовательские возможности доступны всем.
- Личный чат доступен его участникам. Доступ к обращениям поддержки имеют автор, поддержка и администраторы. Роль администратора сама по себе не открывает обычные личные переписки через приложение.
- Аудит административных действий хранится в PostgreSQL. Технические логи API ведутся отдельно с ротацией.
- Аватары пока остаются в PostgreSQL. Для фотографий отчётов планируется S3-совместимое хранилище с серверной обработкой изображений.
- Уведомления открываются мини-окном по нажатию на поплавок. Личные сообщения — в отдельной панели диалогов.
- Рабочий вариант первого VPS: 1 vCPU, 2 ГБ RAM, 25–30 ГБ SSD, Linux и публичный IPv4. Это исходная конфигурация для малой нагрузки; пригодность подтверждаем измерениями.

Redis рассматриваем при появлении нескольких экземпляров API или измеренной потребности в кэше/временных состояниях. ClickHouse — при потребности в аналитике большого потока событий. Основной журнал аудита при этом остаётся в PostgreSQL.

## 3. Последовательность разработки

| Этап | Результат | Зависимости |
| --- | --- | --- |
| 0 | Подготовлена проверяемая базовая версия и уточнены контракты | Текущее состояние проекта |
| 1 | Роли, права и аудит | Этап 0 |
| 2 | WebSocket и мини-окно уведомлений с поплавком | Этап 1 |
| 3 | Личные текстовые диалоги | Этапы 1–2 |
| 4 | Чат поддержки и рабочее место оператора | Этапы 1–3 |
| 5 | Завершённые основные сценарии форума и модерации | Этап 1; события используют этап 2 |
| 6 | Профили, подписки и восстановление доступа | Этапы 1–3 |
| 7 | Фотографии отчётов и законченный рыболовный сценарий | Этапы 1 и 5–6 |
| 8 | Проверенная публичная бета на VPS | Критерии выпуска ниже |

Инфраструктурную часть этапа 8 можно готовить с начала работ. После этапа 4 возможна закрытая альфа на основе уже работающего текстового форума; публичная бета требует прохождения критериев выпуска.

### Этап 0. Базовая версия и контракты

- [x] Зафиксировать текущие сборки web/API и регрессионные проверки в CI (workflow добавлен; удалённый запуск проверяется после push).
- [ ] Сменить ранее раскрытые SMTP-реквизиты и секрет подтверждения; хранить действующие значения только в окружении/локальных секретах.
- [ ] Проверить реальную регистрацию: письмо доставляется, код проверяется, сессия появляется автоматически. Подтвердить SPF/DKIM/DMARC по доставленному письму.
- [ ] Уточнить состояния обращений и правила прочтения сообщений/уведомлений. Матрица полномочий реализована в [ролях и аудите](ROLES_AND_AUDIT.md).
- [ ] Описать будущие REST-операции в OpenAPI, а WebSocket-события — отдельным контрактом с примерами и версией формата.
- [ ] Обновлять фактическую модель данных вместе с миграциями: текущий `DATA_MODEL.md` содержит первоначальную концепцию.

**Готово, когда:** есть воспроизводимая проверка исходного состояния, перечень новых операций и согласованные правила доступа. Отсутствие ещё не арендованного VPS не блокирует разработку следующих этапов.

### Этап 1. Роли, полномочия и аудит

- [x] Добавить модель совмещаемых ролей и миграцию существующих `user/moderator/admin` без потери доступа.
- [x] При регистрации выдавать только пользовательские права; назначение ролей разрешить администраторам.
- [x] Добавить команду первоначального назначения администратора на сервере и защиту от удаления последнего административного доступа.
- [x] Реализовать общие серверные проверки полномочий для HTTP и будущего WebSocket. Блокировка аккаунта остаётся отдельным статусом.
- [x] Добавить `audit_events`: исполнитель, время, действие, объект, причина, request ID и разрешённые сведения об изменении.
- [x] Успешные служебные изменения и аудит сохранять в одной транзакции. Содержимое личных сообщений, пароли, коды и токены в аудит не записывать.
- [x] Добавить просмотр журнала для администратора с фильтрами и пагинацией. API редактирования/удаления событий не предоставлять; правила хранения определить до автоматической очистки.

**Готово, когда:** пользователь не может повысить себе роль; модератор и поддержка имеют разные полномочия; ошибка записи аудита отменяет служебное изменение. Права проверены тестами на нескольких аккаунтах.

### Этап 2. Уведомления и общий канал реального времени

- [ ] Реализовать чтение одного уведомления, чтение всех до зафиксированной границы и точный счётчик непрочитанных.
- [ ] Добавить WebSocket с действующей сессией и проверкой Origin. Получателей событий определяет сервер.
- [ ] Учесть ограничения текущего HTTP-транспорта: общий `WriteTimeout` 30 секунд, совместимость middleware с Upgrade и настройки Caddy.
- [ ] Предусмотреть heartbeat, переподключение, ограничения размера/частоты событий и ограниченные очереди медленных клиентов.
- [ ] Отправлять события после commit. Если используется PostgreSQL LISTEN/NOTIFY, применять его как сигнал об изменении; сами уведомления и сообщения хранить в таблицах.
- [ ] Восстанавливать пропущенное через историю, устранять дубли по ID и синхронизировать прочтение между вкладками.
- [ ] Закрывать соединения/отзывать доступ при выходе, блокировке и изменении полномочий.
- [ ] Заменить переход на отдельную страницу уведомлений открытием мини-окна. Старый путь `/notifications` должен открывать тот же центр уведомлений для совместимости ссылок.
- [ ] На desktop показать окно рядом с поплавком, на мобильном — удобную панель. Поддержать фокус, Escape, закрытие снаружи и возврат фокуса.
- [ ] Добавить SVG-поплавок: короткий нырок, круги на воде и подсветка при новом событии. Непрочитанные обозначать счётчиком; учитывать reduced motion и объединять всплеск нескольких событий.

Открытие окна не помечает всю историю прочитанной. Старые записи при первоначальной загрузке не запускают анимацию нового события.

**Готово, когда:** уведомление появляется без обновления страницы, переживает обрыв связи и не попадает другому аккаунту. Проверены повторное подключение, logout, отзыв роли и одновременное поступление нового уведомления во время «прочитать все».

## 4. Проверки и критерии выпуска

Каждая функциональная задача включает соответствующие миграции, контракт API/событий, обработку ошибок и проверки прав. Крупные этапы разбиваются на небольшие проверяемые коммиты.

Обязательные проверки по характеру изменения:

- PostgreSQL-интеграция и Go race detector для прав, транзакций, сообщений и событий.
- Проверки изоляции нескольких пользователей: REST, WebSocket, личный кэш, смена аккаунта, блокировка и отзыв ролей.
- Сетевые сценарии: повтор операции, потеря соединения, восстановление истории и отсутствие дублей.
- Frontend build и браузерные проверки новых сценариев на 393 и 1440 px, с клавиатурой и понятными ошибками.
- Для загрузок — реальные повреждённые/слишком большие изображения и отсутствие EXIF/GPS в публичном результате.

Публичная бета готова после этапов 0–7 и завершения инфраструктурной ветки: работает регистрация/восстановление доступа, форум, личные сообщения, поддержка и уведомления; проверены права и приватность, реальная доставка почты, HTTPS и восстановление резервной копии.
